# 2026-10-07 — Data API rejected a large batch during the first backfill (HTTP 413)

## Summary

The first full production backfill replayed 153 stored raw runs (100,268 tracks). The run for the largest week failed: one `BatchExecuteStatement` carried every source relation of that run, and the Data API rejects request bodies over 4 MiB with HTTP 413. The live canonicalization worker shares the code path and would have failed the same way on an equally large week.

## Impact

152 of 153 runs replayed; one week was not refreshed until the fix. No data was lost: the raw object stayed in S3 and the run could be replayed. The payload size was not recorded.

## Timeline (UTC+4)

- 09:51 — `9cdce94` makes identity and entity writes set-based (one round-trip per phase), which made batches as large as a whole run.
- 16:05 — the backfill feature merges (PR #252).
- After the merge — the first production apply (8 min 20 s) reports 152/153.
- 16:36 — `e69fa10` splits batches under a byte budget.
- 17:15 — the re-run is documented: 153/153.

## Root cause

`DataAPIClient.batch_execute` built one request from all parameter sets with no size cap.

## Fix

`e69fa10`: `batch_execute` splits parameter sets into consecutive chunks under `_BATCH_REQUEST_BYTES` (3,000,000 bytes, headroom for ARNs, SQL and JSON framing), each sent with the caller's transaction id and the Data API retry policy; an oversized single set goes alone. Pinned by `test_batch_execute_splits_requests_under_the_data_api_size_limit` and `test_batch_execute_sends_an_oversized_parameter_set_on_its_own`.

## Detection gap

Neither the fake Data API client nor the real-Postgres stand-in models the 4 MiB limit, and test weeks are small. Only a production-sized week reached it.

## Follow-ups

- Done: the fix lives in the shared client, so the live worker is covered too.
- Done: [`docs/scalability.md`](../scalability.md) measures Data API calls per 1,000 tracks and shows where the next limit is: 10× the largest week still fits the Lambda timeout, 100× needs chunking.
- Open: no metric records batch sizes; the budget is a constant.
